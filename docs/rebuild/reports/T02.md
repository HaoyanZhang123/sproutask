## 实现与范围

新增包 `@edu/storage`（`education/packages/storage/`，package.json `type: module`、唯一 public entry `src/index.ts`、`dependencies` 为空）：

1. **单写者 JSONL journal**（`src/journal.ts`、`src/lock.ts`、`src/paths.ts`）：`journal/events.jsonl` 每行一个完整 command；append 在 `writeSync + fsyncSync` 成功后才返回确认；`seq` 由存储递增分配，不信任客户端时钟；`requestId` 在打开时重建持久索引，重放同一 requestId 返回原 receipt（`duplicate:true`，原 seq/eventId），不重复计数；`events.lock` 基于 `openSync('wx')` 的独占锁，第二实例/进程返回 `CONFLICT`，关闭时按 token 释放；崩溃遗留锁仅在其 pid 已死亡时回收，无法解析的锁仅在 stale TTL 后回收；写失败（注入 ENOSPC）返回 `STORAGE_FAILED`（retryable），且不推进 lastSeq、不回滚成假确认。
2. **两阶段 attempt/assessment**（`src/attempts.ts`）：`attempt.submitted` 先写原答 + `feedback:{state:'pending'}`（落盘即确认已保存）；`assessment.committed` 将 Assessment + Evidence + 进度/复习 effects 写入**同一 journal 行**，落盘才确认；`assessment.failed`/`assessment.cancelled` 只改 pending 状态、不判错、不新建 attempt；提交用 `attemptId|graderVersion|revision` 去重；取消后的迟到 assessment 被 `CONTRACT_REJECTED` 拒绝；commit 后不得再 fail/cancel；重试只重做同一 attempt 的批改。

## 失败与返工

本轮验收运行无失败；开发轮修复的问题（均为本卡 scope 内，不删用例/不放宽标准）：

1. **首次 9 failed：assessment 证据跨 attempt 被误拒**。复现：`supported` assessment 的两条 Evidence 来自两个不同 attempt，commit 却要求 Evidence.attemptId 必须等于 assessment.attemptId。原因：把“两次活动证据”误当成单 attempt。修复：改为校验每条 Evidence 的 learner/edition/pack/concept 绑定，并要求其 attempt 已先 `attempt.submitted`；保留“两个不同 attempt”由 domain `validateAssessmentWithEvidence` 在 T06 判断。
2. **mid-corruption 读取跨洞返回后续 commit**。原因：domain 分类器报告 corrupt 行，但 storage 直接把分类后的 commits 全量返回。修复：只读模式使用 `goodPrefixCommits` 截到损坏点之前，测试从 2 条期望改为 1 条良好前缀，不静默跳过坏行。
3. **删除越界目标返回 STORAGE_FAILED 而非 CONTRACT_REJECTED**。原因：路径校验异常落入通用 catch。修复：先解析/校验全部目标，`StoragePathError` 映射为 `CONTRACT_REJECTED`；删除执行错误仍为 `STORAGE_FAILED`。
4. **迁移只读 journal + 缺失源路径的返回码顺序**。修复：先校验输入源，再检查 writable；缺失源为 `INVALID_INPUT`，只读 journal 为 `CONTRACT_REJECTED`。
5. **attempt 测试只保存了第一条 attempt 就提交跨两条 attempt 的证据**。这是测试准备错误，不是实现放宽；改为先提交 bundle 中全部 attempt，再提交 assessment，断言相应 seq 后移。

### B-02 删除计划未按 scope 复算

- **原缺陷**：`deleteData(plan, true)` 只校验 `plan.targets` 每条都在 storage root 内，没有用 `plan.scope` 重新计算规范目标集。`DeletePlan` 是普通对象；调用方篡改 targets（保持 root 不变）即可删除 root 内非 scope 目录（如 `receipts`/教材资产目录），违反“删除学习记录不得误删教材源/共享内容”。
- **修复**（`src/maintenance.ts`）：
  1. 抽出 `scopeRelativeTargets(scope)`，`prepareDelete` 与 `deleteData` 共用同一 scope→相对目标映射。
  2. `deleteData` 内部用 `expectedDeleteTargets(plan.scope)` 复算目标；每个目标经 `resolveInside` + `assertDeleteTarget`（realpath、阻止 symlink 逃逸、拒绝 root 本身）得到规范绝对路径。
  3. 实际 `plan.targets` 同样规范化后做**集合全等**校验（Windows 路径大小写不敏感比较；检测缺失、额外、重复目标）；不一致直接拒绝，返回 `code=CONTRACT_REJECTED`、message 前缀 `DELETE_PLAN_MISMATCH`、`detailsRef=delete-audit:<planId>`（domain 的 `SERVICE_ERROR_CODES` 是封闭联合，本卡范围不允许改 domain，故用稳定子码前缀暴露语义）。
  4. **只删除复算得到的规范目标**；即使 `plan.targets` 顺序/大小写不同，也不会删除任何未复算命中的路径。
  5. 新增审计 `receipts/delete-audit.jsonl`：拒绝时记录 `outcome=rejected`、错误子码、expected/provided 目标；成功时在删除前写 `DELETE_AUTHORIZED`（审计写失败则中止删除、不触碰数据），删除后写 `DELETE_COMPLETED` 与 `deletedTargets`；`DeleteReceipt` 增加可选 `auditPath`（向后兼容）。root 不符、target 越界、scope 解析失败等拒绝也会尽量留审计。
- **测试**（`test/export-delete.test.ts`，新增 3 条 + 成功用例加审计断言）：
  - `rejects a forged plan that adds another root-internal target (B-02)`：scope=journal 的 plan 追加 `receipts` → 拒绝；journal/snapshots/receipts 均未删除；审计最后一条为 rejected、`TARGET_SET_MISMATCH`、expected=1/provided=2。

### M-01 `readFrom` 未按 learner 过滤

- **原缺陷**：`EventStore.readFrom(ctx)` 仅按 `seq > fromSeq` 过滤，不使用 `ctx.learnerId`；同 root 下任意持有者可读到其他 learner 的 journal 行；`latestSeq` 也返回全局 seq。
- **修复**（`src/journal.ts`）：
  1. `readFrom` 先按 `commit.learnerId === ctx.learnerId` 过滤，再按 seq/limit 分页；`hasMore` 只统计该 learner 的剩余行。
  2. `lastSeq`/`latestSeq` 改为 learner 作用域（该 learner 最大 seq；无行返回 0），不泄露其他 learner 的活动量。
  3. 分页游标：部分页时 `lastSeq` 返回本页最后一条 seq（避免 T06 `readAll` 用全局最大 seq 跳行）；完整页返回该 learner 最新 seq。
  4. 未知 learner 返回空 commits、`lastSeq=0`，不报错也不泄露他人行。

## § 锁自愈（F8）2026-10-31

### 原故障

真实事故：残留 `learner-data/journal/events.lock` 时插件无法启动。旧实现只在“锁内 pid 已死”时回收；若该 pid 已被无关进程复用（`process.kill(pid, 0)` 成功），会永久返回 `CONFLICT: journal is locked by pid …`，且没有任何审计记录，用户只能手工删锁。

### 修复

1. **默认 TTL 120 s**：`DEFAULT_LOCK_STALE_MS = 120_000`；`OpenStorageOptions.lockStaleMs` 可配置（测试中用更短值验证边界）。
2. **回收规则**（`education/packages/storage/src/lock.ts`）：
   - pid 已死 → 立即回收，原因 `holder_dead`；
   - pid 存活但锁年龄（文件 mtime 与记录 createdAt 取较大者）超过 TTL → 视为 pid 复用/陈旧锁，回收，原因 `stale_timeout`；
   - 无法解析的锁 → 只有超过 TTL 才回收，原因 `unreadable_lock`；未超时仍拒绝且不删除别人的锁。
3. **心跳避免误抢活锁**：持有锁时每 `max(1 s, staleMs/3)` 重写锁元数据（刷新 `createdAt`）并刷新 mtime（timer `unref()`），`release()` 清理 timer。这样长时间运行的合法进程不会被 TTL 判为陈旧，只有崩溃/冻结超过 TTL 的锁才会被回收。
4. **审计 `lock.reclaimed`**：
   - `AcquireLockOptions.onAudit` 接收 `{ kind:'lock.reclaimed', subject, reason, detail:{pid,ageMs,staleMs,token} }`；
   - `StorageService.open` 新增 `onAudit`，`composeEducationRuntime` 转发宿主 `onAudit`，宿主已有 `log({event:'edu.audit', payload})` 写入运行时审计日志；
   - `RecoveryReport`/`StorageStatus` 增加可选 `lockReclaimed`，`recoverySteps` 增加 `lock.reclaimed:<reason>` 行，诊断界面/日志可见。
5. **测试**（`education/packages/storage/test/journal.test.ts`，新增 3 条）：
   - 伪造“pid=当前进程、锁 mtime=2020 年”的复用锁 → 能启动，`status.lockReclaimed.reason='stale_timeout'`，捕获到 1 条 `lock.reclaimed`；
   - 伪造不可解析锁 + 超 TTL → 能启动，原因 `unreadable_lock`；
   - 活跃锁（pid=当前进程、mtime 新）→ `CONFLICT`，不产生审计、不删除原锁。
   - 原“死进程锁可回收”用例保留（`spawnSync` 取已退出 pid）。

### 未完成 / 边界

- TTL 是启发式：如果持锁进程被冻结/暂停超过 `lockStaleMs`，另一个实例仍可能回收并写入；本轮用“活进程心跳 + TTL”降低风险，但没有 OS 级文件锁或跨主机的租约机制。
- 回收年龄取锁文件 mtime 与元数据 `createdAt` 的较大值，`now` 来自注入 clock；若系统时钟大幅回拨，可能推迟回收（不会误删活跃锁，因为活跃锁有心跳）。
- 未做真实插件进程崩溃/重启的端到端演练；本轮是隔离临时数据根的离线单测。
- 未改 contract-lock、未 `pnpm install`、未重生锁文件。
