# 需求规格（specs）

每条需求一份文件，命名 `F-0XX-<名称>.md`。**先写 spec，再写代码。**

## 为什么

这个项目的实现会分散在多次、甚至多个不同的 AI 对话里完成。
spec 是"同一条需求在不同时间、不同对话里被实现"时唯一不跑偏的依据：
它固定了**边界（做什么 / 不做什么）**和**验收标准（怎么算做完了）**。

## 使用方式

1. 复制 `F-000-template.md` 起一份新 spec，编号在 `docs/ROADMAP.md` 的 Backlog 里认领
2. 实现完成后，把验收清单逐条勾掉，并补一行实测结论（如"实测：exe 双击可启动，耗时 3s"）
3. 如果实现中发现 spec 写错了：**先改 spec，再改代码**，并把原因写进"变更记录"

## 与 ADR 的分工

| 文档 | 回答的问题 | 什么时候写 |
|---|---|---|
| spec | 这一条需求要做什么、怎么验收 | 每条需求，动手前 |
| ADR | 为什么这样搭架构、为什么放弃另一个方案 | 契约/架构变更时 |
